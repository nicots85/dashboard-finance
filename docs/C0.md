# C0 — Protección de datos antes del rediseño

Esta etapa protege los datos. El diseño nuevo, VWAP y fotos del tablero se
implementarán después de la confirmación del usuario. No se activó una tarea
diaria en ninguna máquina: el usuario todavía debe indicar cuál será la principal.

## 1. Qué se guarda y qué no se borra

- Las velas acumuladas no tienen limpieza automática por antigüedad.
- Si la fuente corrige una vela que ya se había recibido **terminada**, se
  conserva su valor anterior, el nuevo, los campos que cambiaron y cuándo se
  observó la corrección, en `candle_corrections`.
- La finalización normal de una vela que se recibió abierta no se presenta como
  corrección histórica. Se determina por la fecha en que se recibió, el horario
  de su mercado y su zona real, incluidos los cambios de hora estadounidense.
- Un nuevo precio, volumen o fuente cambia la versión de esa serie. Repetir
  exactamente los mismos datos no cambia su versión.
- No se borraron ni redescargaron velas reales para estas pruebas.
- El registro comienza en C0: no recupera valores anteriores que ya habían sido
  reemplazados antes de esta etapa.
- El formato antiguo de recepción no verificaba bien UTC: en esta Mac podía
  adelantar la hora tres horas. Las escrituras nuevas usan UTC correcto. Si una
  vela antigua cambia, se conservan ambos valores y se marca que no se pudo
  comprobar si su recepción anterior era provisional; no se inventa esa hora.

## 2. Copia manual o automática

Desde la carpeta del proyecto, con el entorno activado:

```bash
python backup_data.py
```

La copia usa **el método de respaldo de SQLite**, incluye las escrituras
confirmadas aunque la base esté usando sus archivos temporales, y se comprime
en ZIP con un comprobante de integridad y cantidades. No se copia a ciegas el
archivo abierto.

Las copias quedan fuera de Git en:

```text
backups/
  daily/    hasta 7 días distintos
  weekly/   hasta 4 semanas distintas
  monthly/  hasta 3 meses distintos
```

Se conserva la copia más nueva de cada período; siete actualizaciones de hoy
no reemplazan siete días. Las fechas de los archivos están en UTC. El mismo
respaldo se conserva en los tres grupos: puede haber copias del mismo contenido.
Solo se eliminan copias anteriores después de completar el respaldo nuevo.
Los archivos ajenos al patrón de respaldos no se tocan.

La carpeta y cantidades son editables en `config/operations.yaml`. También se
puede elegir otra carpeta con `python backup_data.py --destino "ruta"`.

Además, `update_data.py` hace una copia automática **antes de la primera
actualización de cada día** si todavía no existe una de ese día. Si falla el
respaldo, no inicia la descarga. Esto no sustituye programar la copia diaria
cuando no se abre la app ni se actualizan datos.

## 3. Programar la copia diaria: Mac

**Hacerlo solo cuando se haya elegido esta Mac como máquina principal.**

1. Abrir Terminal en la carpeta del proyecto.
2. Activar el entorno:

   ```bash
   source .venv/bin/activate
   ```

3. Probar la copia manual:

   ```bash
   python backup_data.py
   ```

4. Preparar la tarea sin activarla:

   ```bash
   python install_daily_backup.py --hora 21:15
   ```

5. Activarla en esta máquina:

   ```bash
   python install_daily_backup.py --hora 21:15 --instalar
   ```

6. Verificar que aparece «Tarea instalada». La definición se guarda también en
   `backups/schedule/`. Mac ejecuta la copia mediante `launchd`: no hace falta
   tener Streamlit abierto. Se realiza también al iniciar la sesión del usuario.
7. Revisar `backups/logs/backup-daily.log`, el archivo de errores y las fechas de
   los ZIP al día siguiente.

La hora es **la hora local de la computadora**. Si usa Buenos Aires, 21:15
significa 21:15 de Buenos Aires. Se requiere equipo encendido y sesión de usuario
iniciada; si está dormido, la tarea se puede ejecutar al despertar. Una máquina
apagada no puede crear copias. No se programó despertar automáticamente al equipo.

Para desactivar, desde Terminal:

```bash
launchctl bootout "gui/$(id -u)" "$HOME/Library/LaunchAgents/com.dashboard-finance.backup.plist"
```

Si se mueve el proyecto o cambia la ubicación de Python, volver a instalar la tarea.

## 4. Programar la copia diaria: Windows

**Hacerlo solo cuando se haya elegido esta PC como máquina principal.**

1. Abrir PowerShell en la carpeta del proyecto.
2. Activar el entorno:

   ```powershell
   .venv\Scripts\Activate.ps1
   ```

   Si Windows impide activarlo, ejecutar directamente `.venv\Scripts\python.exe`
   en lugar de `python` en los comandos siguientes, sin cambiar permisos del sistema.

3. Probar y preparar la tarea:

   ```powershell
   python backup_data.py
   python install_daily_backup.py --hora 21:15
   ```

4. Activarla:

   ```powershell
   python install_daily_backup.py --hora 21:15 --instalar
   ```

5. Abrir **Programador de tareas → Biblioteca** y buscar
   `DashboardFinanceRespaldoDiario`.
6. Elegir **Ejecutar** para probarla. Revisar «Último resultado» y que haya un
   ZIP reciente en `backups/daily/`.
7. En sus propiedades, comprobar que «Ejecutar la tarea lo antes posible si no
   hubo un inicio programado» está activo. El instalador lo deja habilitado.

La tarea usa el Python del entorno virtual y admite rutas con espacios.
Funciona sin Streamlit, con el equipo encendido y el usuario conectado.
La hora es la hora local de Windows; no se habilita despertar al equipo.

Para desactivar, desde PowerShell:

```powershell
schtasks /Change /TN DashboardFinanceRespaldoDiario /DISABLE
```

La definición XML se genera y prueba automáticamente, pero su ejecución real
en Windows debe comprobarse en la PC elegida; este trabajo se hizo en Mac.

## 5. Probar una restauración sin tocar la base real

Elegir un destino que no exista, por ejemplo:

```bash
python restore_data.py --ultimo --destino data/restauracion_prueba.db
```

La herramienta verifica el ZIP, su comprobación, la integridad de SQLite, las
cantidades de **todas** las tablas y la fecha del último dato. Si falla algo,
no instala el archivo. No reemplaza un destino existente sin `--reemplazar`.

Para elegir una copia específica:

```bash
python restore_data.py "backups/daily/finance_FECHA_HORA.zip" --destino data/restauracion_prueba.db
```

## 6. Restaurar de verdad, paso a paso (Mac y Windows)

1. Cerrar Streamlit: `Ctrl+C` en su terminal. Cerrar cualquier descarga o cálculo
   y desactivar temporalmente la tarea programada.
2. Conservar una copia actual: `python backup_data.py`.
3. Elegir la copia por su fecha. Primero probarla con el comando del apartado 5.
4. Restaurar ese **mismo archivo** a la base real:

   ```bash
   python restore_data.py "ruta/al/respaldo_elegido.zip" --destino data/finance.db --reemplazar
   ```

   No usar `--ultimo` después de crear la copia del paso 2 si se quiere volver
   a una copia anterior: hay que elegir explícitamente el archivo deseado.

5. La herramienta conserva también un respaldo de la base anterior en
   `backups/before_restore/`, con la misma retención. Si hay archivos SQLite
   `-wal`/`-shm`, SQLite intenta confirmar y cerrar sus archivos temporales. Si
   hay procesos usándolos, se detiene: **no borrarlos a mano**. Cerrar esos procesos
   y volver a intentar.
6. Abrir la app y comprobar fechas. Si la copia es anterior a C0, el programa
   conservará los datos y avisará que los cálculos necesitan verificarse de nuevo.
7. Recalcular con `python run_calc.py` y reactivar la tarea diaria.

Los datos posteriores a la copia elegida no forman parte del respaldo. Se puede
volver a descargar lo que aún conserve la fuente, sin prometer recuperar 1m antiguo.

## 7. Fechas y resultados desactualizados

Régimen, dispersión, cointegración y macro guardan:

- Fecha y hora del cálculo.
- Fecha del último dato **usado** (para pares, la última vela coincidente).
- Versiones de las series usadas, incluidos ambos activos de un par.
- Parámetros usados y su identificador.
- Estado «calculable/no calculable» y motivo del error si corresponde.

Una corrección histórica también invalida el resultado aunque el último cierre
no cambie. Repetir datos idénticos no lo invalida. Cambiar los parámetros pide
recalcular. Los cálculos anteriores a C0 no reciben una versión ni una hora
inventada: se conserva el registro antiguo y se marcan «recalcular para comprobar»;
no se presenta su hora antigua dudosa como fecha de cálculo verificada.

En la app, revisar el aviso superior y **Fechas de cálculo y datos usados**.
El semáforo y la tabla ahora leen la misma versión guardada; no mezclan un
semáforo recalculado con una tabla vieja. El caché se invalida si cambian precios
o resultados. Los errores de cointegración se muestran como **No calculable**.

```bash
python check_data.py
```

Muestra correcciones registradas, avisos de descarga y resultados que requieren
recalcular. Las fórmulas de régimen/z no cambiaron; se evitó calcular toda la
historia de percentiles cuando solo se necesita el último. Las pruebas comparan
la salida con el cálculo histórico a diez decimales.

## 8. Huecos y límites

Los avisos quedan en `data_notices`, con primera/última fecha y resolución.
Una descarga vacía no se anuncia automáticamente como «al día». Los errores y
descargas parciales producen salida no exitosa para que la app los muestre.

- Se detectan huecos de cripto continua, posibles saltos dentro de la misma
  rueda de mercados y cortes largos. No se inventan velas faltantes.
- No se confunden noches/fines de semana normales con pérdidas.
- Es una detección conservadora, no certifica el calendario completo de todos
  los feriados ni identifica por sí sola cada día entero ausente.
- Yahoo avisa si su límite impidió recuperar parte del tramo solicitado.
- Cripto avisa límites de carga inicial y si se alcanzaron 200 páginas antes
  de llegar al presente. Una ejecución nueva puede continuar desde lo guardado.

Las fechas, avisos y registros de corrección están en la base y en su respaldo.
Los límites de descarga nunca ejecutan una limpieza de velas acumuladas.

## 9. Historia para cointegración (antes de implementar los estados)

```bash
python check_cointegration_history.py
```

Solo lee la base. Cuenta precios coincidentes y positivos y retira las velas
finales todavía abiertas. Tener suficientes bloques no confirma una relación:
solo permite evaluarla. También habrá que revisar la cobertura dentro de cada bloque.

| Par | 1h: bloques de 1.000 | 4h: bloques de 500 | 1D: bloques de 500 |
|---|---:|---:|---:|
| Nasdaq / S&P | 3 | 2 | 20 |
| S&P / Dow | 3 | 2 | 17 |
| Nasdaq / Russell | 3 | 2 | 19 |
| Oro / Plata | 11 | 6 | 13 |
| Oro / Cobre | 11 | 6 | 13 |
| Tecnología / Consumo | 3 | 2 | 13 |
| Financiero / Industrial | 3 | 2 | 13 |
| Bitcoin / Ethereum | 79 | 40 | 6 |
| Ethereum / Solana | 53 | 26 | 4 |
| Bitcoin / Solana | 53 | 26 | 4 |

Conteo al 2026-10-05. Cinco bloques requieren 5.000 velas en 1h o 2.500 en
4h/1D. El contraste de 1.000 en diario requeriría 5.000 para cinco bloques.
Los pares con Solana no alcanzan cinco bloques diarios.

Los metales **sí** alcanzan técnicamente los bloques intradía por sus jornadas
mucho más largas. Se deja documentada la diferencia y la restricción del usuario:
por ahora la futura clasificación se habilitará solo en diario y en cripto
intradía donde alcance. No se afirma falsamente falta de historia en metales;
se informará que esa evaluación intradía no está habilitada por el alcance acordado.
Argentina no evalúa cointegración local/ADR: mantiene CCL. Sus cálculos antiguos
de pares se conservan, pero no se usan ni se reactivan en esta etapa.
